# Docker builds with BuildKit

Use BuildKit cache mounts for SwiftPM's dependency cache and build directory. Keep
the Swift toolchain version the same as the version used by the project and copy
the package manifests before source files so dependency resolution can use a
separate Docker layer.

```dockerfile
# syntax=docker/dockerfile:1.7
FROM swift:6.2-jammy AS build
WORKDIR /workspace

COPY Package.swift Package.resolved ./
RUN --mount=type=cache,id=swiftpm-cache,target=/root/.cache/org.swift.swiftpm,sharing=locked \
    --mount=type=cache,id=swift-build,target=/workspace/.build,sharing=locked \
    swift package resolve

# The build context must include every local package input, such as sources,
# plugins, macro implementations, resources, and local packages.
COPY . .
RUN --mount=type=cache,id=swiftpm-cache,target=/root/.cache/org.swift.swiftpm,sharing=locked \
    --mount=type=cache,id=swift-build,target=/workspace/.build,sharing=locked \
    swift build -c release --product MyApp && \
    mkdir -p /out && cp .build/release/MyApp /out/MyApp

FROM swift:6.2-jammy-slim AS runtime
COPY --from=build /out/MyApp /usr/local/bin/MyApp
ENTRYPOINT ["/usr/local/bin/MyApp"]
```

Replace `MyApp` with the executable product name. Copy any additional local
package directories or resources needed by the manifest; do not omit macro or
build-tool plugin inputs. Keep `.build` out of the Docker build context with
`.dockerignore` so host artifacts are not copied into the image.

The named cache mounts persist between BuildKit builds and can reuse SwiftPM
checkouts and compiler outputs. A cache mount is temporary storage for a build
step and is not committed to the image layer. The example copies the executable
to `/out`, which is outside the `.build` mount, before the final stage copies it
into the runtime image. Do not use `COPY --from=build /workspace/.build/...`
when `.build` is mounted as a cache.

The manifest-first copy keeps the dependency-resolution layer reusable when
only application sources change. The `.build` cache then lets SwiftPM rebuild
changed targets incrementally. Keep the same cache IDs across builds; use
`sharing=locked` when concurrent builds may write to the same cache.

## Resolve only the Pearfy module dependencies you use

Pearfy declares optional SwiftPM package traits for dependencies used by
PostgreSQL, Redis, TLS transports, and the game-server gRPC modules. Projects
created with `pearfy new` start with the small HTTP module set. `pearfy add`
and `pearfy remove` update both the selected Pearfy products and the traits in
the managed `Package.swift` dependency declaration. For example, a service
that does not add `gameserver-grpc` does not resolve gRPC packages.

For a manually maintained SwiftPM manifest, pass only traits required by the
Pearfy products in the target. A minimal HTTP application generated by the
Pearfy CLI uses the NIO server, public macros, and Crypto-backed data contracts,
so it enables `Crypto`, `Macros`, and `NIO`. Add `Postgres`, `Redis`, `NIOSSL`,
or `GameServerGRPC` only when the selected module graph requires them:

```swift
.package(
    url: "<PEARFY_REPOSITORY_URL>",
    from: "<version>",
    traits: ["Crypto", "Macros", "NIO"]
)
```

The URL and version above are placeholders for the Pearfy source and release
used by the application. Existing manifests that omit `traits` keep Pearfy's
default all-module compatibility behavior. Explicit traits require SwiftPM
6.1 or newer. Pearfy's gRPC protobuf Swift sources are checked in, so merely
resolving a non-gRPC Pearfy product does not load the gRPC code-generation
plugin or its dependency graph.

Trait selection reduces dependency resolution and download work; it does not
remove dependencies required by the chosen module graph. BuildKit cache mounts
remain useful after selecting modules because they reuse checkouts and compiler
outputs across builds.

| Trait | Optional dependency family |
| --- | --- |
| `Macros` | SwiftSyntax compiler plugin (also enables `Crypto`, required by macro API types) |
| `NIO` | SwiftNIO transports |
| `Postgres` | PostgresNIO and swift-log (also enables `Crypto` and `NIO`; PostgresNIO currently brings swift-nio-ssl transitively for its TLS support) |
| `Redis` | RediStack plus swift-nio-ssl, swift-log, swift-metrics, and atomics (also enables `NIO`) |
| `NIOSSL` | SwiftNIO SSL (also enables `Crypto` and `NIO`) |
| `GameServerGRPC` | gRPC Swift and SwiftProtobuf (also enables `Crypto` and `NIO`) |

The HTTP CLI starter requests `Crypto`, `Macros`, and `NIO`. A bank API that
also selects PostgreSQL, ledger, and security adds `Postgres`; that graph does
not resolve Redis or gRPC. PostgresNIO currently brings swift-nio-ssl
transitively because it supports TLS itself, even when the Pearfy `NIOSSL`
feature is not selected. RediStack also brings swift-nio-ssl for Redis TLS.
BoringSSL work can remain part of Crypto, PostgreSQL, and Redis builds, so
trait pruning does not remove those costs from modules that require them.

## Regenerate game-server gRPC sources

Generated gRPC and Protobuf Swift files are checked into Pearfy so consumers
that do not select `GameServerGRPC` do not run or resolve the gRPC code
generation plugin. After changing a `.proto` file, regenerate both source sets
from the repository root with SwiftPM 6.2:

```bash
mkdir -p Sources/PearfyGameServerGRPC/Generated Sources/PearfyGameServerAgones/Generated
swift package --allow-writing-to-package-directory generate-grpc-code-from-protos \
  --output-path Sources/PearfyGameServerGRPC/Generated --access-level public -- \
  Sources/PearfyGameServerGRPC/Protos
swift package --allow-writing-to-package-directory generate-grpc-code-from-protos \
  --output-path Sources/PearfyGameServerAgones/Generated --access-level public -- \
  Sources/PearfyGameServerAgones/Protos
```

Review the generated diff and build `PearfyGameServerGRPC` and
`PearfyGameServerAgones` before committing a protocol change.

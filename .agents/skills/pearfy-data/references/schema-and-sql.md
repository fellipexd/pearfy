# Schema and SQL contracts

- `SQLQuery` builders preserve bindings; compose values as parameters and identifiers through `SQLIdentifier`.
- `SchemaIR` is canonicalized and fingerprinted. Entity/table/column/index validation is performed when constructing it.
- `@ManyToOne`, owning `@OneToOne`, inverse `@OneToOne(mappedBy:)`, `@OneToMany(mappedBy:)`, and owning/inverse `@ManyToMany` emit `SchemaEntity.relationships`. `SchemaIR` resolves inverse fields, requires target tables and unique referenced columns, and materializes physical FK columns/constraints or a deterministic many-to-many junction table with a composite primary key. Join-table and FK/column names can be explicit. Join-table keys are non-null; `SET NULL` and `SET DEFAULT` are rejected there. No relationship macro performs runtime loading or persistence; repositories/adapters own access.
- Owning `@ManyToOne` and `@OneToOne` accept `primaryKey: true` to make the generated FK column part of the entity key without a duplicate scalar property. Such columns must be non-null. `SchemaIR` orders relationship key columns first in relationship declaration order, then scalar `@ID` columns in declaration order. Inverse and many-to-many relationships cannot directly join the entity key. Existing-table primary-key changes require an explicit migration (`PEARFY_SCHEMA_021`).
- Relationship references currently target one primary or unique column. Composite referenced keys, ORM fetch/cascade behavior, embedded values, inheritance mapping, and collection ordering metadata are not part of this schema contract; retain explicit reviewed SQL/model metadata for unsupported cases.
- `PostgresSchemaCompiler` generates an initial deterministic plan. Unsupported alterations fail instead of silently guessing destructive semantics.
- Generate migration artifacts from discovered `SchemaEntity` values with `pearfy migrations generate --product <SwiftPM-product> --id <version_name>`. The app product must implement the reserved `--pearfy-export-schema <path>` argument by canonicalizing `PearfyGeneratedSchemaRegistry.entities` as `SchemaIR` JSON. `--model <path>` selects the JSON file to export/read; with `--product` it is the export destination, and without it the file is the desired schema input. Pass `--previous-model <path>` to plan a delta from a saved prior `SchemaIR` snapshot; primary-key changes that cannot be planned safely fail with `PEARFY_SCHEMA_021`. The command does not connect to a database.
- `SQLMigrationCatalog` and `SQLMigrationRunner` live in data/PostgreSQL modules; inspect both before changing migration behavior. Applied artifact checksums and transaction locking are actual contracts; rollback automation is not.
- Model macros describe schema metadata only where the discovery plugin emits it for the target.

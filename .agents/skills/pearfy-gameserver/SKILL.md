# Pearfy game server

Load for a game server using PearfyEngine `PearfyNetwork`. Read `docs/GAMESERVER.md` and inspect the imported product's current source.

## Available behavior

`PearfyGameServer` provides bounded HMAC-SHA256 session tickets, session/player/protocol binding, expiring/revocable tickets, WSS-only offers, in-process rooms with private invitations/reconnect grace, an idempotent server-side command reducer with deterministic replay validation for complete checkpoints, a process-local party-aware matchmaking queue, bounded realtime input with client sequence checks and per-player queue/byte budgets, a monotonic fixed-step driver with a per-tick work cap and no catch-up bursts, a configurable sustained-overrun circuit breaker that closes input admission, fixed-cardinality saturating overload metrics, immediate release of drained input payloads, a co-op objective state machine with bounded acyclic prerequisites, monotonic progress targets, optional seeded SplitMix64 decisions, a server-authored bounded NPC action scheduler, reconnect grace and explicit member abandonment, version-compatible recovery checkpoints, command-ID/player/objective/payload binding, bounded idempotency history and an aggregate public/private state-byte budget, and a single-process zone/entity registry with per-entity fencing epochs. Configurable capacities are hard limits and are not benchmarked throughput claims. Room disconnect notices are idempotent and do not extend the original reconnect deadline; room mutations, snapshots, room counts and public discovery remove expired disconnected members even if the optional reaper has not run. An expired member cannot reclaim the room through reconnect. NPC scheduling stores opaque application actions; the application must author them server-side and supply the authoritative tick loop. Reconnect must be separately authenticated; a disconnected player cannot read snapshots or issue gameplay actions until reconnected. Recovery checkpoints contain private state and seed material; persist them using a recovery adapter outside gameplay ticks and never expose them to clients.
New co-op members join only during the lobby; active sessions resume rostered members through `reconnect`. Reconnect grace is bounded to 24 hours, duplicate disconnect notices do not extend the first deadline, and expiry/abandonment removes that player's private state while retaining the seat until session end. An explicit expiry call cleans up stale members, but reconnect and gameplay authorization enforce the deadline without waiting for a reaper. When all members have abandoned or exhausted grace, the session fails and clears scheduled NPC actions.

`GameServerStateManager` provides a shared singleton or independently configured actor, bounded state retention and ingress, independent asynchronous workers per `GameServerStateMiddleware`, bounded retry with exponential backoff, replacement/failure metrics, state restore before start and graceful drain/flush. Each ingress and middleware mailbox is bounded by both item count and `maximumPendingStateBytes` (1 MiB by default); overflow replaces the oldest pending record. The publisher does no storage I/O and must not be awaited from a game tick. `GameServerStateClosureMiddleware` adapts an application-owned SQL store; it does not define the game's schema or transaction policy.

Use the optional `PearfyGameServerGRPC` product for the TLS unary control plane (`FindGame`, `CreateRoom`, `Join`, `Leave`) and `PearfyGameServerTransport` for WSS gameplay. Both delegate bearer ticket authorization and game rules to async app callbacks. Use `PearfyGameServerRedisRecovery` for Redis Streams, checkpoints, epoch fencing and restore. Use `PearfyGameServerWorldPostgres` for bounded cross-replica MMO zone leases and transactional entity handoff. Use `PearfyGameServerDevKit` to merge manager snapshots into the bearer-protected, paginated DevKit state panel.
Use optional `PearfyGameServerThreatDirector` for deterministic, bounded pressure scoring and finite NPC action recommendations in co-op sessions. Persist its server-only checkpoint through an application-owned durable state path; validate each recommended action against live world state before scheduling. Use `PearfyGameServerNPCLearn` separately when bounded typed Jev choices are needed outside the simulation tick.

## Boundaries

Room/matchmaking/world state, ticket revocation, and command history are in-process by default. Optional PostgreSQL products add cross-replica queue claims and fenced MMO zone/entity state; neither is a simulation tick store. There is no distributed room store, genre-specific simulation, or anti-cheat. `GameRealtimeFixedStepDriver` advances bounded input on a monotonic cadence and does not burst to catch up when processing reaches a later scheduled deadline. Its synchronous application handler must not perform network/storage I/O; overruns are counted and cause simulation time to fall behind wall time. After the configured number of consecutive overruns (three in the CLI presets), the driver stops and closes input admission. A reducer error also fails the driver closed. The application must recover or drain queued inputs, call `resumeInputAdmission()` only when the queue is empty, and create a new driver before accepting more gameplay. The optional `PearfyGameServerRealtime` product provides bounded paginated AOI snapshots and state-reconciliation deltas, but not cross-replica visibility or a network replication protocol. `PearfyGameServerTransport` provides WSS and an authenticated encrypted UDP server codec; PearfyEngine `PearfyNetwork` has a matching secure UDP client codec, but session-secret provisioning and deployed abuse/performance validation remain app responsibilities. High mode leaves UDP disabled until those app-level gates pass. Swift ARC remains enabled in every profile.

State middleware is best-effort asynchronous persistence, not durable-commit acknowledgment. Bounded queues may replace older pending snapshots under pressure. Publish only allowlisted projections: never include tickets, signing keys, credentials, request bodies, cookies, personal data, SQL bindings, sockets or transport state. Redis durability depends on its AOF/RDB/replication settings. App-owned database adapters own their retries and transactions.

## CLI and validation

The CLI provides `pearfy gameserver modules` (Registry-backed status and installability), `pearfy gameserver modes`, `pearfy gameserver template --mode light|medium|high [--output file]`, and `pearfy gameserver recipe turn-based|fps|friendslop|mmo|rooms|dedicated [--output file]`. Templates include explicit bounded fixed-step budgets: 20Hz/128 inputs per tick for light, 30Hz/1,024 for medium and 60Hz/8,192 for high, plus queued-input caps and a three-consecutive-overrun admission circuit breaker. `GameServerModeProfile.makeRealtimeSimulation(initialTick:)` resumes the simulation cursor from a committed recovery tick; `makeRealtimeFixedStepDriver(simulation:handler:)` builds the profile cadence and work cap. Older decoded templates without fixed-step bounds fail closed. The budgets are starter limits, not certified host capacity. `pearfy gameserver recovery --store redis` is dry-run by default and requires a managed project with GameServer and Redis resolved; pass `--apply` to select `gameserver-redis-recovery` and write `.pearfy/gameserver-recovery.json` (or the explicit `--output` path). The generated file contains environment-variable names, never credentials, and calls out best-effort delivery and the lack of a guaranteed RPO. Recipes list composition and app-owned work; they are not automatic module installers or genre implementations. `fps`/`mmo` target high mode and retain the safe UDP-disabled default. Run `swift build` and `swift test --filter 'GameServer|DevKit'`; these validate local behavior, not deployed TLS/transport or Redis crash/failover guarantees.

# PearfyGameServerRedisRecovery

## Contract

- Import `PearfyGameServerRedisRecovery` only when the app opts into the Redis recovery product.
- Own `RedisGameStateRecoveryStore` lifecycle: `start()` before use, `stop()` during shutdown.
- `stop()` waits for an in-flight connection start; concurrent stop calls wait for the same pool/event-loop shutdown to finish. Close Redis only after it returns.
- Before accepting commands for a recoverable session, acquire its exclusive lease with `acquireLease(sessionID:ownerID:durationMilliseconds:)`; use a fresh owner UUID per process lifetime. The returned monotonically increasing epoch fences prior processes. Renew before expiry and release during graceful shutdown.
- Append authoritative `GameStateEvent` records and save checkpoints with the lease epoch. Redis atomically rejects appends/checkpoints with no active lease or an epoch that no longer owns the session. A stale process cannot renew or release the new owner's lease.
- For discrete reducer-based commands, use `RedisDurableGameCommandSession.open(...)` after acquiring the lease. `commit(commandID:playerID:command:expectedRevision:)` computes the next state, appends the event and result digest, then mutates committed in-memory state. Append failure leaves state/revision unchanged; retry an ambiguous response with the same ID/player/command. This call awaits Redis, so keep it in an async command/control task outside the simulation tick.
- For continuous authoritative state, use `RedisDurableGameTickSession.open(...)` and commit `RedisDurableGameTickBatch` values. A batch contains consecutive tick numbers, bounded application-defined transitions (including movement, NPC actions, timers and inventory), and the exact random draws the reducer consumes. One batch is one fenced journal event and replays each tick in order with a digest check. `makeBoundedQueue()` provides finite staging, one-slot coalesced writer notifications and ordered `commitNext()`; a failed/ambiguous append leaves the same batch at the head, and `retryPending()` wakes the writer after its retry policy permits. Commit is write-ahead: do not publish or acknowledge the batch until its receipt succeeds. The app must serialize the producer, drain notifications from a separate async task, apply admission/backpressure at queue capacity, and never call Redis from the simulation tick. This API does not capture transport input or make speculative state durable.
- To stage from `GameRealtimeFixedStepDriver`'s synchronous handler without an actor hop, use `RedisDurableGameTickWriteAheadBridge`. Read `RedisDurableGameTickSession.snapshot().lastCommittedTick`, construct the simulation with `GameServerModeProfile.makeRealtimeSimulation(initialTick:)`, then synchronously call `bridge.stage(batch)` from the tick handler. Start the bridge separately; its serial task commits on Redis and calls `onDurableCommit(batchID, receipt)` only after append acknowledgment. Publish or acknowledge only there, deduplicating external publication by `batchID`. Before publication the bridge verifies that the receipt cursor matches the batch's final tick, so reusing a previously committed batch ID cannot publish its stale receipt as a later tick. The bridge bounds pending batch count and bytes; stage errors close bridge admission and should escape the tick handler so the fixed-step driver also fails closed. A writer or publication failure retains the exact head batch, closes bridge admission and invokes the optional failure callback. `retryPending()` retries the same idempotency key, but admission remains closed; rebuild the simulation from the recovered committed state before accepting gameplay. `stop()` closes staging and waits for an active writer to drain; inspect returned metrics and do not claim a clean drain when pending batches remain.
- Actor-backed deterministic domains can use `RedisDurableGameCommandSession.openAsync(...)`. The session holds its per-session commit gate across reducer suspension, then appends before publishing the next state; reducer failure or concurrent commit/checkpoint fails without advancing the journal.
- `RedisDurableGameCoopSession` adapts bounded co-op lifecycle and mission commands (join/start/reconnect/abandon/objective progress/completion/server-authored NPC scheduling/finish) to write-ahead Redis commits. Open from an initial `GameCoopSession` or recover by session ID after acquiring the new lease. It uses the outer command ID for both the Redis idempotency ledger and the co-op objective dedupe key, and restores per-player visibility through `snapshot(for:)`. `deterministicDecision(commandID:playerID:expectedRevision:)` appends a seeded decision before returning its SplitMix64 value keyed by the committed journal sequence; retries return the same value, including after checkpoint/recovery. The player must be an active session member and the session must have a seed. Keep durable decisions off simulation ticks; this API does not wrap per-frame input, NPC schedule drains, or the in-memory `nextDeterministicValue()` draw path.
- The durable command actor serializes one unresolved append per session and rejects concurrent commits/checkpoints with `commandCommitInProgress`; callers must apply backpressure or retry. Its bounded idempotency window is checkpointed with state. It replays journal suffixes through the same deterministic reducer and checks each resulting-state digest. This is for discrete commands, not per-frame FPS/MMO input.
- Tick and queue configuration caps state bytes, encoded batch bytes, ticks and transitions per batch, transition bytes, random draws, idempotency entries, replay work, pending batches and retained queue bytes. Tick numbers must be contiguous with the last queued/committed tick. The application reducer remains responsible for validating the transition schema and replaying the exact server-authoritative movement/NPC/timer rules; never treat client state as a transition.
- Store versioned app-defined state in bounded `GameStateCheckpoint` values. Invoke snapshots outside the realtime tick.
- Checkpoints larger than 256 KiB are base64 encoded into 256 KiB Redis string chunks and published through a versioned manifest containing byte counts and a SHA-256 digest. Redis validates chunk presence and publishes the manifest/watermark atomically under the active lease; replaced chunks are removed after commit. Existing single-value base64 checkpoints remain readable.
- Chunk restore uses one bounded `MGET` of at most 256 chunks, verifies exact sizes and SHA-256 before decoding, and fails closed for missing, corrupt or oversized chunks. The checkpoint JSON and base64 staging are still materialized in process memory before splitting, bounded by `maximumRecordBytes`; this is not incremental world serialization.
- On recovery, load the checkpoint and events after its revision, then replay with the application's deterministic reducer. Validate event sequence and schema before publishing recovered state.
- Recovery scans the stream in byte-aware `XRANGE` pages (maximum 128 records and an 8 MiB estimated page budget); each base64 record is bounded against `maximumRecordBytes` before decoding. `maximumRecoveryBytes` caps the total scan. Keep `maximumRecordBytes` near the actual event size so restore batches remain useful.
- A fresh leased session with no checkpoint, sequence or stream entries restores as empty. Missing checkpoint with existing sequence/stream data, or malformed/oversized checkpoint data, fails closed with `invalidResponse`, `recordTooLarge` or `recoveryLimitExceeded`; it never silently starts an empty world over existing journal data.
- Choose the Redis persistence, replication and failover policy based on the required recovery point objective. Redis Streams do not alone guarantee zero loss during failover. Lease expiration fences writes but does not itself migrate a session or replay the recovered state.
- For non-loopback hosts, enable `tlsEnabled` and provide a valid certificate `serverName`; the adapter requires full server certificate verification. Password authentication without TLS is limited to loopback connections.
- Keep tickets, signing keys, player credentials, sockets and transient transport state out of snapshots and events.
- Bound input command/state bytes, stream length, checkpoint cadence and recovery replay work. Monitor append failures without logging payloads.
- The stream has an exact event cap. If uncheckpointed events reach that cap, append fails with `journalCapacityReached`; it never trims events that are still required for recovery. Save a checkpoint and apply the application's durable-input/backpressure policy before accepting further state changes.
- `RedisGameServerStateMiddleware` checkpoints after `checkpointEvery` persisted events or, when `checkpointIntervalMilliseconds` is configured, on the first state update after that interval. Time-based checkpointing is event-triggered while idle because unchanged state has no newer watermark. `flush()` saves the latest state during graceful shutdown.
- Call `checkpoint()` on the durable command session on a bounded maintenance cadence. Do not confuse its write-ahead command path with the state's best-effort newest-wins projection middleware.
- Projection revisions are monotonic per retained `(namespace, key)`: older revisions are rejected before journal append, an identical revision/payload is idempotent, and reusing a revision for different payload bytes fails with `projectionRevisionConflict`. These checks protect projected state ordering; they do not turn the middleware into a durable game-command transaction or substitute for application event persistence.
- `GameStateRecoveryCheckpointScheduler` runs a bounded periodic capture on an async maintenance task, outside the simulation tick. The capture closure must return a checkpoint whose revision is the latest journal sequence included in that captured state; publish the corresponding events durably before allowing the checkpoint to cover them.
- Start and stop the scheduler with the session lifecycle. `checkpointNow()` performs a single bounded capture and write; overlapping captures are rejected. Oversized snapshots are rejected before store I/O. Metrics expose only successful/failed counts and the last successful timestamp.
- The scheduler does not append events, acquire/renew leases, restore application state, or guarantee a final checkpoint on stop. Call `checkpointNow()` explicitly before `stop()` when shutdown requires a final snapshot. Its interval controls checkpoint cadence, not recovery-point guarantees; Redis persistence and app event-ack policy still determine the RPO.

## Limits

This package implements the adapter, fencing checks, bounded stream append and checkpoint load/store, plus an opt-in asynchronous checkpoint scheduler, bounded write-ahead tick batches and a bounded async-writer staging queue. It does not provide a simulation loop, capture client inputs, place sessions across nodes, or configure Redis persistence. A returned Redis command response is not proof that data survives host or replica loss; operational durability depends on Redis configuration.
